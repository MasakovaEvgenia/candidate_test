### 2. Добавлен шаг подготовки данных

```ruby
Given(/^удаляю пользователя с логином (\w+\.\w+) если он существует$/)
```

Шаг проверяет наличие пользователя на сервере и удаляет его при необходимости.

Это для того, чтобы исключить падения при повторных запусках (если пользователь уже был создан ранее, то есть для чистоты теста).

### 4. Выявленные особенности / несоответствия API

В ходе тестирования зафиксированы расхождения между ожидаемыми и фактическими HTTP-статусами.

Важно: данные расхождения я рассматривала именно как потенциальные дефекты, если иное не указано в спецификации API.

| Ситуация | Ожидаемый статус | Реальный статус | Комментарий |
|----------|-----------------|-----------------|-------------|
| Создание пользователя с существующим логином | 409 Conflict | 400 Bad Request | Нарушение уникальности логина трактуется как конфликт состояния |
| Изменение пользователя с пустым именем | 422 Unprocessable Entity | 400 Bad Request | Запрос валиден по формату, но не проходит бизнес-валидацию |

## Исправления в исходном коде (без исправлений тесты не выполнялись)

### Проблема 1: Отсутствовал метод `compile_full_url`

Отсутствовал вспомогательный метод для формирования полного URL запроса, из-за чего HTTP-методы (`GET`, `POST`, `PUT`, `DELETE`) не могли корректно работать.

**Где:** `rest_wrapper.rb`  
**Ошибка:** `undefined method 'compile_full_url'`

**Решение:**
```ruby
private

def compile_full_url(current_url)
  url + current_url
end
```

---

### Проблема 2: Использование устаревшего ID пользователя

После удаления и повторного создания пользователя в кэше сохранялся старый ID, что приводило к ошибке `404`.

**Где:** шаг `изменяю у пользователя параметры`

**Причина:** кэш не обновлялся перед повторным использованием

**Решение:**
```ruby
@scenario_data.users_id[login] = nil
```

Добавлена принудительная очистка кэша перед повторным поиском пользователя.

---

### Проблема 3: Ошибка парсинга JSON в негативных сценариях

Метод `send_error` всегда пытался парсить ответ как JSON, но при ошибках API мог возвращать HTML, что приводило к `JSON::ParserError`.
(это может быть спефицика в проекте, надо смотреть документацию, а может быть и багом как пример неконсистентности api)
**Где:** `rest_wrapper.rb`, метод `send_error`

**Решение:**
```ruby
if body && body.strip.start_with?('{', '[')
  # парсим JSON
else
  # не парсим, фиксируем только статус ответа
end
```

Добавлена проверка формата ответа перед парсингом.

---

### Проблема 4: Отсутствовала проверка статуса ошибки в шагах

Добавила механизм проверки HTTP-статуса для негативных сценариев.

**Решение:** реализован отдельный шаг для валидации кода ошибки

```ruby
Then(/^получаю ошибку (\d+)$/) do |expected_status|
  $logger.info("Проверка: ожидался статус #{expected_status}")

  if @last_error_status != expected_status.to_i
    raise "Ожидался статус #{expected_status}, но получен #{@last_error_status}"
  end

  $logger.info("Статус #{expected_status} совпадает с ожидаемым")
end
```
